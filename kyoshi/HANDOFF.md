# kyoshi — 音声×キャンバス授業プランニングエージェント 引き継ぎドキュメント

新スレッドでこのプロジェクトを開始するための引き継ぎ資料。元になった議論は interview リポジトリの Type 5（自然音声インタビュー）開発スレッドで行われた。

---

## 1. 何を作るのか（ビジョン）

教師とリアルタイム音声で会話しながら、**共有キャンバス（Excalidraw想定）に図を描き、教科書ページを一緒に見て、授業プランを共同設計する**音声エージェント。

参考イメージ: 音声AIがユーザーと話しながらExcalidrawをリアルタイム操作し、会話の意図をその場で図解していくデモ（アーキテクチャ図を描きながら相談に乗る様子）。これの「教師の授業づくり相談」版。

コンセプトの一言: **Type 5 のエージェント（耳・頭脳・声）に「目」と「手」を足す。**

- **目（2系統）**
  - 構造としての目: キャンバス上の要素（ボックス・矢印・テキスト）はJSONで頭脳に渡す。画像認識より速く確実で安価。ユーザーが手で描き足した差分もここで「見える」
  - 画像としての目: 教科書ページ等の資料はマルチモーダルLLMにページ画像として渡す（Gemini Flash系は画像入力対応、現行の脳ルートのまま拡張可）
- **手**
  - 頭脳が発話と並行して構造化された描画コマンド（JSON DSL）を出力し、ホストがキャンバスに反映
  - LLMに自由座標を吐かせると崩れるので、「ボックス・矢印・レーン」程度に制約したDSL＋ホスト側自動レイアウトが定石
- **振る舞い**
  - 発話は即座に始め、描画はワンテンポ遅れて反映（人間も「こういうことですよね」と言いながら描き始める）。レイテンシー設計的にも楽

## 2. 土台: interview リポジトリの Type 5 アーキテクチャ

Type 5 は「ユーザー発話 → 単一音声モデル → 音声返答」の一体型（Type 1/2）をやめ、役割を分離した構成。**kyoshi はこの資産の上に建てる。**

```
事前リサーチ → 耳（ASR+VAD専任） → 頭脳（推論LLM） → 声（日本語TTS）
```

### 毎ターンの脳への入力（現行）

`会話履歴（直近24ターン） + リサーチ資料（最大9,000字） + 章ヒント + 前ターンの仮説メモ` → 出力は `発話文 → --- → 仮説メモ`。

kyoshi ではここに **「キャンバス状態JSON」「開いている資料ページ画像」** を足し、出力に **「描画コマンド」** チャンネルを足す。3部構成（発話 → 描画JSON → 仮説）にするか、描画専用ターンを並走させるかは初期の設計判断。

## 3. 設計上の合意事項（元スレッドでの議論の結論）

1. **発話ファースト**: 音声のレイテンシーを最優先。描画は遅れて反映してよい
2. **キャンバスは構造データで読む**: 画像認識はキャンバスには使わない。教科書・手描きラフにだけ使う
3. **教材は事前処理**: 読み込み時に全ページを一度だけ解析して「ページごとの内容メモ（図の説明込み）」をテキスト化。会話中は「開いているページの画像1枚＋全体メモ」だけを毎ターン渡す（トークン・レイテンシー対策）
4. **グラウンディング規律を最初から入れる**: 「教科書の図では〜」と言ってよいのは実際にページにあるものだけ。interview で実装した引用ホワイトリスト＋決定論ガードの考え方を流用する
5. **モデル戦略**: 毎ターンの発話は Gemini Flash（速度）。事前処理（教材解析）はレイテンシー耐性があるので強いモデル（Fable 5 / GPT-5.5 クラス）を使う価値が最も大きい。比較計測には `scripts/compare-thinking.ts` の手法が流用できる

## 4. 未決定事項（新スレッドで最初に決める）

- **キャンバス技術**: Excalidraw 埋め込み（`@excalidraw/excalidraw`、手描き風・ユーザー直接編集可、推奨候補）/ tldraw（プログラマブルAPIが最も整っている、ライセンス表記条件あり）/ 自前SVG（依存なし最速検証、ユーザー編集不可）
- **コード共有方式**: `kyoshi/` を同一 Next.js アプリ内のルート（`src/app/kyoshi/`）として作るか、`kyoshi/` を独立アプリにするか。**既存の hooks / lib / api を import で再利用するなら同一アプリ内ルートが圧倒的に楽**（モノレポ分割は後からでもできる）
- **PoCのスコープ**: 最小構成は「音声会話＋脳がボックスと矢印を描く」まで。教科書ビューアは第2段階でよい

## 5. 教訓（interview 開発で踏んだ地雷。kyoshi でも同じ穴がある）

1. **コンテキストの切り詰めに注意**: 脳に渡すリサーチ資料を2,200字で切り詰めていたせいで、ミッション欄が脳に届かず、「ミッションを引用しろ」という指示との矛盾で**モデルが捏造で従う**事故が起きた。賢いモデルほど矛盾命令に「作文」で従う。**渡しているつもりのコンテキストが本当に全部届いているかを必ず確認する**（kyoshi ではキャンバスJSONやページメモで同じ事故が起き得る）
2. **プロンプトだけで捏造は止まらない**: 禁止ルールを何層書いてもすり抜ける。**決定論的な出力ガード**（許可リスト照合・差し替え）を出口に置くのが最終防衛線
3. **VADの沈黙検知だけではターンテイキングは成立しない**: 言い淀み・考え込みをテキストで判定して待ち時間を変える適応デバウンス＋発話の取り下げが効いた
4. **ストリーミングが止まって見えるときはモデルの thinking 設定を疑う**: Gemini は `thinking_level: minimal` にしないと最初のトークンまで数秒固まる
5. **Realtime モデルの自動応答は必ず殺す**: `createResponse: false` にしないと脳と二重発話になる

## 6. 環境メモ

- 開発サーバー: `npm run dev`（現在ポート3006で稼働中のことがある。重複起動注意）
- `.env.local` の主要キー: `INTERVIEW_BRAIN_MODEL=gemini-3.5-flash`, `INTERVIEW_BRAIN_THINKING_LEVEL=minimal`, `INTERVIEW_PREP_MODEL=gpt-5.5`（＋OpenAI / Gemini / TTS各社のAPIキー）
- テスト: `npx vitest run`、型: `npx tsc --noEmit`
- クライアント向け説明資料: `docs/type5-executive-summary.md`（Type 5 の対外的な説明トーンの参考に）

## 7. 提案する最初のマイルストーン

1. **M0 — 構成決定**: キャンバス技術とコード共有方式を決定（上記「未決定事項」）
2. **M1 — 話しながら描く最小ループ**: 既存 Type 5 セッションを複製し、脳の出力に描画コマンドチャンネルを追加 → キャンバスに反映。題材は「アーキテクチャ図を描きながら相談」で可
3. **M2 — キャンバスの目**: キャンバス状態JSONを毎ターン脳に還流。ユーザーの手描き編集に言及できることを確認
4. **M3 — 教材の目**: PDF/画像アップロード → ページごと事前解析（強いモデル）→ 会話中はアクティブページ画像を脳に添付。「このページの図」を参照した提案ができることを確認
5. **M4 — 授業プラン特化**: システムプロンプトと進行（章クロック相当）を「授業設計の弧」（ねらい → 導入 → 展開 → まとめ → 評価）に置き換え
